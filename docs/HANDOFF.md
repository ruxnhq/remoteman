**The full-screen lag, found (later that night).** The owner: "moving windows lags", still with variable refresh off, and their mouse reports at **8000 Hz**. Measured with a synthetic mouse (`C:\rm\tools\sweep.ps1 -Hz 8000`): full screen sent about 2000 places a second and spent a quarter of its thread on the state, the window about 920; the Mac test host's log had **up to 3100 a second during the owner's full-screen drags** against 600-950 from the window, each made into its own CGEvent (and a power-manager call). ## 2026-11-24: AV1 through Direct3D 12 for AMD (issue #3; branch `d3d12-av1`, written, never built or run)

The tester's Radeon 780M in a GPU-PV guest: `--probe-av1` said Direct3D 12 encodes AV1 there (Main, P010, CBR, one reference, width a multiple of 64 and height of 16, values reported after encoding `0x137`), while AMD's Media Foundation AV1 and HEVC encoders are listed and can't be made (`0x80070057`). So `d3d12av1.rs` is an AV1 encoder beside `d3d12enc.rs`'s HEVC, ported from Mesa's Direct3D 12 AV1 encoder (`src/gallium/drivers/d3d12/d3d12_video_enc_av1.cpp`, `d3d12_video_encoder_bitstream_builder_av1.cpp`, `d3d12_video_encoder_references_manager_av1.cpp`) and checked by hand against the AV1 specification.

- **What it writes:** the driver writes tile data only. The host writes the temporal delimiter, the sequence header before each keyframe, and each frame's header from the values the driver reports in the resolved metadata (frame metadata, then the tiles' entries, then the tile layout, then the post-encode values: Mesa's order). One tile, no order hints, no screen content tools, single reference, `primary_ref_frame` none on every frame.
- **References:** the decoder's eight slots are tracked. A keyframe fills all eight; each later frame refers to the newest kept picture and replaces one slot holding a picture no longer kept (or held twice). Keeping and anchors work as in `d3d12enc.rs`, so a loss is still answered without a keyframe.
- **Sizes:** AV1 has no crop, so a size the driver's multiples don't divide is refused and the session takes HEVC as before. On the 780M, 3840x2160 and 2560x1440 pass that check (nothing has been encoded yet); 3440x1440 and 1920x1080 don't.
- **Off by default:** `--d3d12-av1` or `REMOTEMAN_D3D12_AV1=1` turns it on (for the service: its registry key's `Environment` value). AV1 is first in `MODES`, so a broken header would turn a working HEVC session into a black picture.
- **`--probe-av1-encode DIR [--probe-size WxH]`:** 240 frames of a moving test picture per GPU, with a loss and a rate change, written to `DIR\av1-N.obu` for `ffmpeg -i av1-N.obu -f null -`. This is how to check it on a card, or in the tester's guest.
- **Not done:** compiled (not even `cargo xwin check`), run on any card, or decoded by any viewer. (The unused-slot value `0xff` is Mesa's `UNUSED_VIRTUAL_DPB_SLOT_PHYSICAL_INDEX`, "as per D3D12 spec"; the service passes its own environment, registry `Environment` included, to the host it starts.)

## 2026-11-25: the viewer crashed on a title-bar drag after a session (Reactor patch 10)

The installed viewer crashed now and then: Windows' event log has `remoteman.exe` access violations in `Microsoft.UI.Xaml.Controls.dll` at the same place since 11/21 (three on 11/25). Both crash dumps looked at (`%LOCALAPPDATA%\CrashDumps`, read with `cdbX64.exe` from WinDbg's package and Microsoft's symbols) show the same stack: a press on the title bar starts Windows' move loop, the window's `WindowRectChanged` runs WinUI's `TitleBar::UpdateIconRegion`, and `TitleBar::GetAppWindowId` reads a freed TitleBar (its inner pointer `0x1`). The app drops its `TitleBar` from the tree for a session (`app.rs`, `view`) and makes a new one after; WinUI's TitleBar never removes its `WindowRectChanged` handler, so a freed one is called on the next move, which crashes or not depending on what has taken its memory. Fixed in the vendored Reactor (VENDORED.md, patch 10): a destroyed TitleBar's element is kept for the life of the UI thread; out of the tree its `XamlRoot` is null, which `GetAppWindowId` checks (seen in its code), so the old handler does nothing. One element per session is kept.
